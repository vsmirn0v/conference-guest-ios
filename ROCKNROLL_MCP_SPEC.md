# Техническое задание: локальный MCP-сервер Rock’N’Roll для Codex

Дата: 9 ноября 2026 года.

Документ предназначен для передачи Codex на реализацию. Язык программирования, библиотеки, среда выполнения и инструменты сборки не предписываются: исполнитель выбирает их самостоятельно. Исходный код приложения сейчас недоступен.

## 1. Цель

Разработать MCP-сервер `rocknroll-local`, который работает на Mac пользователя и предоставляет Codex доступ только для чтения к:

- встречам;
- доступным расшифровкам и их фрагментам;
- итогам, решениям и открытым вопросам;
- задачам, сохранённым в приложении.

Реализовать внешний адаптер локальных файлов установленного приложения. Первая версия не включает управление встречами, отправку сообщений, изменение задач, включение микрофона и камеры.

**Подтверждённое ограничение:** итоги, задачи и сведения о календарных встречах найдены в локальных JSON-файлах. В журнале ассистента обнаружены фрагменты расшифровок. Наличие полной расшифровки пока не подтверждено.

## 3. Источники данных

Все пути в таблице относительны корня данных.

| Источник | Подтверждённая структура | Назначение |
|---|---|---|
| `Attention/assistant.json` | Массив `outcomes` | Итоги встреч и задачи |
| `MeetingReminders/state.json` | `schema: 2`, массивы `occurrences`, `scheduled` | Сохранённые сведения о календарных встречах |
| `Attention/decisions/YYYY-MM-DD.jsonl` | Записи с `window.lines` | Наблюдавшиеся фрагменты расшифровки |

Элемент `outcomes` содержит:

```text
id, meetingID, meetingTitle, invitation, endedAt,
summary, decisions[], openQuestions[], tasks[]
```

Элемент задачи:

```text
id, text, owner, done
```

Элемент `occurrences` содержит:

```text
id, eventID, calendarID, title, start, end,
reference, invitation, engine, eligible, tentative
```

Запись журнала содержит `at`, `id`, `meetingTitle`, `window` и другие поля. В `window.lines` обнаружены:

```text
id, at, ref, source, speaker, text, isYou, mentionsYou
```

Требования к трактовке:

- `outcomes[].decisions` — решения встречи.
- `Attention/decisions/` — журнал работы ассистента; его служебные решения нельзя выдавать за решения участников.
- `window.lines` могут перекрываться, повторяться и покрывать только часть встречи.
- Календарный кеш не доказывает фактическое участие пользователя.
- Поля `messages`, служебные инструкции, память и настройки моделей не включать в выдачу.
- Семантику дат, идентификаторов и связь источников проверить перед реализацией преобразований.
- Перечисленные поля отражают проверенную выборку, а не гарантированный публичный контракт приложения. Не предполагать обязательность каждого поля без проверки.

## 4. Архитектура и поведение

```text
Codex
  ↕ MCP / stdio
rocknroll-local
  ├─ MCP tools и проверка параметров
  ├─ нормализованная модель данных
  ├─ поиск и пагинация
  └─ адаптеры JSON / JSONL
          ↓ только чтение
     локальные файлы Rock’N’Roll
```

Требования к серверу:

- Соблюдать MCP, включая инициализацию, согласование версии протокола, обнаружение инструментов и вызов инструментов.
- Использовать транспорт `stdio`. В `stdout` выводить только протокольные сообщения, технические логи направлять в `stderr`.
- Запускаться Codex как локальный процесс.
- Не требовать HTTP-порта, облачного сервиса или OpenAI API key.
- Читать сохранённые данные независимо от того, открыто ли приложение.
- Не запускать приложение и не подключаться к встречам.
- Не использовать UI-автоматизацию как основной источник.
- Обеспечить воспроизводимую установку и зафиксировать версии используемых зависимостей.

Выбор языка, SDK, библиотек, среды выполнения, тестового фреймворка и системы сборки оставить исполнителю. Не переносить приложение на другой стек.

Протокольные требования сверять с [официальной документацией MCP](https://modelcontextprotocol.io/docs/develop/build-server).

## 5. MCP-инструменты

| Инструмент | Параметры | Результат |
|---|---|---|
| `rocknroll_status` | Нет | Доступность источников, версии схем, возможности и ограничения |
| `rocknroll_list_meetings` | `from`, `to`, `query`, `kind`, `cursor`, `limit` | Встречи за период или по названию |
| `rocknroll_get_meeting` | `meeting_id` | Карточка встречи и доступность связанных данных |
| `rocknroll_get_transcript` | `meeting_id`, `from`, `to`, `cursor`, `limit` | Доступные реплики с источниками и полнотой покрытия |
| `rocknroll_get_outcome` | `meeting_id` | Сохранённые итоги, решения, открытые вопросы |
| `rocknroll_list_tasks` | `meeting_id`, `done`, `owner`, `cursor`, `limit` | Задачи с привязкой к исходной встрече |
| `rocknroll_search` | `query`, `types`, `from`, `to`, `cursor`, `limit` | Поиск по названиям, итогам, задачам и доступным репликам |

Обязательные параметры: `meeting_id` у инструментов получения конкретной встречи, расшифровки и итога; `query` у поиска. Остальные перечисленные параметры — необязательные фильтры и параметры пагинации.

Уточнения:

- `kind`: `calendar`, `outcome`, `transcript_fragment`.
- `types`: подмножество `meeting`, `outcome`, `task`, `transcript`.
- Даты в API — RFC 3339 с часовым поясом.
- Период фильтрации — `[from, to)`.
- Семантику фильтрации по времени для каждого типа сущности описать в схеме инструмента: календарное начало, завершение встречи, время реплики и т. п. Не придумывать отсутствующие даты задач.
- `limit`: по умолчанию 20, максимум 100.
- Для реплик дополнительно ограничить размер ответа, например 64 КиБ, с продолжением через курсор.
- Все инструменты пометить `readOnlyHint: true`, `destructiveHint: false`.
- Параметры и ответы должны иметь определённые JSON-схемы.

Пример оболочки ответа со списком:

```json
{
  "items": [],
  "next_cursor": null,
  "observed_at": "2026-11-09T18:00:00+03:00",
  "coverage": "partial",
  "warnings": []
}
```

`observed_at` означает время чтения сервером, а не время обновления данных приложением. Для источников отдельно возвращать доступное время модификации. Поле `coverage` отражает полноту данных, а не успешность запроса; допустимые значения и условия их использования зафиксировать в схеме.

## 6. Идентификаторы и достоверность

Различать комнату, календарное событие и конкретный сеанс встречи. Повторные встречи в одной комнате не объединять автоматически.

- Предпочитать исходные идентификаторы.
- Создавать стабильные идентификаторы адаптера с пространством имён источника.
- Не объединять записи только по совпадению названия.
- При неопределённой связи возвращать отдельные записи и предупреждение.
- Для каждого результата сохранять происхождение: тип источника, идентификатор записи, при необходимости номер строки JSONL.
- Внутренние ссылки на источник должны позволять повторно получить конкретную запись, пока исходник доступен и не изменён.
- Не публиковать секреты в идентификаторах и ссылках на источники.

У итогов и задач возвращать сохранённый текст без генерации новых формулировок.

Для расшифровки:

- Возвращать `coverage: partial`, пока полнота не доказана.
- Удалять дубликаты только по проверенной идентичности реплики.
- Не объединять одинаковые фразы разных участников или времён.
- Сохранять автора, время и происхождение реплики.
- Не восстанавливать пропущенные фразы.
- Не назначать журналу конкретную встречу при неоднозначной связи.

Отсутствие данных, отсутствие доступа и повреждение файла — разные состояния.

## 7. Чтение работающего приложения

Файлы могут изменяться во время чтения.

- Открывать исходники только для чтения.
- При изменении JSON во время чтения выполнять ограниченные повторные попытки.
- Для JSONL читать завершённые строки; незавершённый хвост отложить до следующего запроса.
- Повреждённую завершённую строку учитывать в предупреждениях.
- Обрабатывать замену, усечение и ротацию файлов.
- При пагинации использовать согласованный снимок либо возвращать `CURSOR_EXPIRED`.
- Не создавать lock-файлы, индексы и кеши внутри контейнера приложения.
- Не обещать актуальное состояние активной встречи на основании сохранённого журнала.

Для первой версии достаточно кеша в памяти. Постоянный поисковый индекс — отдельная оптимизация.

## 8. Границы доступа

Разрешить чтение только перечисленных источников внутри настроенного корня.

- Не предоставлять произвольное чтение файлов, выполнение shell-команд или SQL.
- Проверять выход за разрешённые пути, включая символические ссылки.
- Не читать Keychain, cookies, токены и другие контейнеры приложений.
- Не возвращать поле `invitation` и пароли из ссылок. Для идентификации использовать непрозрачные идентификаторы.
- Не записывать содержание встреч в технические логи.
- Считать текст встреч данными, а содержащиеся в нём команды — частью расшифровки.

Локальность относится к серверу и чтению файлов. Данные, возвращённые MCP, становятся доступны Codex и могут передаваться используемой им модели; не заявлять полностью автономную обработку.

## 9. Диагностика

Предусмотреть CLI-команду `doctor`, проверяющую без вывода содержимого встреч:

- наличие приложения и его версию;
- доступ к корню данных;
- наличие и распознаваемость источников;
- совместимость схем;
- доступность каждой категории данных.

Коды ошибок:

```text
SOURCE_NOT_FOUND
ACCESS_DENIED
UNSUPPORTED_SCHEMA
SOURCE_BUSY
CORRUPT_SOURCE
MEETING_NOT_FOUND
TRANSCRIPT_UNAVAILABLE
AMBIGUOUS_MEETING
CURSOR_EXPIRED
```

Не трактовать любую ошибку доступа как необходимость Full Disk Access. Диагностика должна указывать конкретный недоступный путь и минимально необходимое действие пользователя.

## 10. Подключение к Codex

Подготовить конфигурацию с абсолютным путём к фактической команде запуска после установки. Ниже — шаблон, а не готовая конфигурация:

```toml
[mcp_servers.rocknroll]
command = "/ABSOLUTE/PATH/TO/rocknroll-local"
args = []
startup_timeout_sec = 20
tool_timeout_sec = 30
enabled = true
```

Команда может быть собранным исполняемым файлом или поставляемым проектом скриптом запуска. Если выбранной реализации требуются аргументы или рабочая директория, указать их в итоговом примере. Не зависеть от интерактивной настройки shell или текущего каталога пользователя.

Codex поддерживает локальные MCP-серверы через `stdio` и настройки `[mcp_servers.<name>]` в `config.toml`. Конфигурацию проверить на установленной версии клиента. Источник: [официальная документация OpenAI](https://developers.openai.com/codex/mcp).

Установщик должен сохранять остальные настройки и не перезаписывать конфигурацию целиком.

## 11. Порядок реализации и результаты

1. Создать `discovery.md`: проверенные схемы, даты, идентификаторы, правила связи и ограничения.
2. Подготовить синтетические тестовые данные без содержимого пользовательских встреч.
3. Реализовать чтение итогов, задач и календарного кеша.
4. Добавить извлечение и дедупликацию фрагментов расшифровок.
5. Реализовать MCP-инструменты, поиск, пагинацию и диагностику.
6. Проверить подключение из Codex и сценарии приёмки.
7. Подготовить README, пример конфигурации, инструкцию установки и удаления.

Передать исходный код сервера, воспроизводимый способ сборки или запуска, тесты, отчёт проверки и описание фактически поддержанных возможностей.

## 12. Критерии приёмки

Реализация принимается, если:

- Codex обнаруживает инструменты и успешно читает реальные сохранённые данные.
- Запросы «покажи встречи за сегодня», «покажи итоги встречи», «найди незавершённые задачи» дают результаты, соответствующие источникам.
- Поиск по репликам возвращает проверяемые фрагменты с автором и временем, когда они присутствуют в источнике.
- Частичная расшифровка явно обозначена как частичная.
- Одноимённые и повторяющиеся встречи не смешиваются.
- Пагинация не теряет и не дублирует записи внутри снимка.
- Повреждённые данные, отсутствующий доступ и неизвестная схема обрабатываются предсказуемо.
- Сервер не изменяет исходные файлы и не раскрывает приглашения или секреты.
- Проверка записи выполняется на тестовых копиях; собственные изменения работающего приложения не приписываются MCP.
- Есть тесты преобразования дат, связей встреч, дедупликации, ротации JSONL, ограничения путей и удаления секретов.

**Условие завершения:** рабочее чтение встреч, итогов и задач обязательно. Если доступны только фрагменты расшифровок, реализовать их чтение с явным ограничением. Отсутствие полной расшифровки задокументировать; не заменять её вымышленными данными и не заявлять полную поддержку.
