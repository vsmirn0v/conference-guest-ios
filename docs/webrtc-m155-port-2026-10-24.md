# M155 SDK port — 24 October 2026

This is an isolated development candidate. Both shipping framework pins, the opt-in native Mac engine setting, and the iOS engine defaults remain unchanged. No publication or promotion is authorized by this experiment.

## Identity and scope

Jitsi `v155.0.1`, source `623fcfe044d5037b3ecd92001c2ef80ca1d932d5`, archive SHA256 `2b7d74ad4d5a3050ff71a8b2b5af86fadaab7576c24c02ab3a2de2a63692f437`. Builds use the target DEPS, LLVM24 `llvmorg-24-init-7747-g62397f8b-27`, and fresh output directories. The existing M150 compiler/dependency checkout is not used as an ABI substitute. Identical dependency file bytes were APFS-cloned to save disk space.

The previous 14/23 patch-application result was a source compatibility trial, not a qualified SDK replacement. This port includes the missing ordered audio lifecycle changes, atomic screen-sender update, and required LiveKit SDK APIs: AudioEngine/InputMixer and processing-state APIs, frame/data crypto, desktop capture, HEVC, simulcast, receive control, camera/view helpers, and configuration/transceiver accessors.

M155 already contains the essential old `0008` restart-status repair and `0011` reentrant SDP callback fix. Those are recorded as upstream-satisfied rather than duplicated. The new crypto port uses M155 frame metadata and timestamp variants instead of restoring a removed virtual `header()` ABI. The legacy any-address ICE property maps to M155 allocator flags, preserving unrelated flags; custom injected allocators remain outside that legacy property's compatibility guarantee.

## Review

Astra xhigh reviewed the plan and implementation. Its findings led to real fixes and focused regressions for active-track processing updates, AudioEngine communication defaults, formal audio processing constraints, and receive pause aliases. Build validation additionally exposed interface placement, thread annotation, buffer accessor and protected factory-state accessor gaps. All source review results remain distinct from test execution.

ABIs are interchangeable.

Loopback probes each send 150 synthetic frames and resize from 320×180 to
640×360 halfway through. Every codec produced at least 20 frames at each size,
with advancing timestamps and the requested codec confirmed in RTP statistics:

| Target/flavor | H.264 frames | VP8 | VP9 | HEVC |
| --- | ---: | ---: | ---: | ---: |
| Mac guest | 142 | 149 | 147 | 148 |
| Mac prefixed | 141 | 149 | 147 | 148 |
| Simulator guest | 133 | 149 | 148 | Not run |
| Simulator prefixed | 133 | 149 | 147 | Not run |

These are correctness checks, not throughput benchmarks. HEVC ran through
VideoToolbox on the native Mac. Simulator observations do not establish iPhone
hardware acceleration or battery efficiency.

Build and integration checks exposed and fixed missing data-cryptor compilation,
Mac framework header packaging, incomplete HEVC advertisement, native namespace
collisions, and a Mac Metal view that was declared but not compiled. Compiling
the unified view also exposed a private `frameRotation` helper conflicting with
`NSView.frameRotation`; it is now `rtcVideoFrameRotation`, with no public API
change. Astra's final focused review found no remaining blocker in those changes.

The first broad media run failed because strict test fixtures did not expect the
new legitimate audio-layer query, and two configuration assertions assumed
protobuf was enabled. Narrow expectations and build-aware assertions fixed the
fixtures without suppressing strict mocks, skipping cases or changing production
behavior. Initial failures and subsequent successful evidence are retained.

## Compatibility limits and remaining acceptance

Native Mac live results are recorded in
[the separate live-validation report](webrtc-m155-live-validation-2026-10-24.md).
Real microphone/camera transport, normal-AEC audio lifecycle, two-way video and
bounded reconnect/soak runs have now been exercised. Intermittent RTC/transport
failures and incomplete sharing acceptance remain explicit promotion blockers;
this does not replace the wrapper, app-level or physical iPhone gates below.

The arm64 simulator guest-wrapper audit resolves all 39 actual RTC imports,
with no duplicate RTC exports or wrapper-referenced legacy method differences.
It compares 67 exported legacy classes and 1,017 methods. It still records
8 absent legacy selectors and 29 encoding differences, none referenced by the
audited wrappers. Some concern private/native C++ interfaces. This static audit
does not prove dynamically constructed calls, C++ layout or wrapper runtime
compatibility; do not promote based on symbol resolution alone.

Before replacing a shipping pin, run live native Mac and guest-wrapper
conferences with real microphone/speaker echo cancellation, mute/route changes,
camera/Presenter/sharing resize, repeated reconnect/UDP/TCP soak, interruptions
and clean Leave. Validate the iPhone/device slice, Bluetooth/cellular/background
recovery, and quality/latency/energy on physical hardware. Catalyst, x86_64 and
on-screen Retina equivalence are not qualified by these native arm64 Mac and
arm64 simulator checks. No battery or quality improvement is claimed.
