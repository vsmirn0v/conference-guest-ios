# Validation record — 23 September 2026

Build under test: pinned public iOS SDK `salute-developers/jazz-ios-sdk@6d5f92869690fa22bb489a9089aa554d733c6936` (25.3.1020); Xcode 27.0; signed with development team `5V64BP2H3P` on the connected `iVitalii` iPhone. No live invitation password, SDK key or token broker is stored in this repository.

| Check | Observed result |
| --- | --- |
| Anonymous browser trace | `/user/info` returned `authType: ANONYMOUS`; the guest join page fetched room public info and posted a password-bearing anonymous `/preconnect` request. The origin's well-known service document identified its conference backend. This is direct trace evidence for the web flow, not a promise of public protocol stability. |
| Native anonymous authorization | With the pinned SDK, an empty-string `.jazzToken` callback joined the supplied guest-enabled meeting. No account login or SDK project key was needed in this test. |
| Invitation decoding | Passing the URL's encoded `psw` directly as `JazzRoom(decodedPassword:)` crashed in the SDK password coder. Using `JazzSession.shared.handle(url:type:.applink)` decoded it and joined. The crash path is removed. |
| Endpoint derivation | The SDK default host was `jazz.sber.ru`; the invitation origin's well-known document resolved a different backend, `bk.salutejazz.ru`, and the signed app joined through that discovered host. The backend is not hardcoded in app settings. |
| Device build and join | Automatic signing, device build, install and launch succeeded. The native view showed two participant tiles and compact in-call controls. A second browser participant listed the phone with microphone Off and camera Off. The user's later observed microphone-on state resulted from manual enabling on iOS. |
| Native deeplink | A cold `conferenceguest://join?url=…` launch via `devicectl --payload-url` opened the signed app and populated the original HTTPS invitation; the Join screen reported the meeting ready. This did not test Universal Link association. |
| Initial background baseline without CallKit | Opening Safari initially retained two browser participants. After a longer background period with both local streams off and the other participant muted, the browser listed only itself. Foregrounding the app restored the phone. Exact disconnect/rejoin timing was not instrumented. |
| Background with inbound audio | A second Chrome endpoint used a synthetic microphone and appeared as an active speaker. The muted phone remained in the browser participant list for several minutes while Safari was foregrounded on the phone. When that browser microphone was muted, the backgrounded phone disappeared from the list within about a minute. This strongly associates the failure with the absence of active incoming media; exact SDK/OS suspension cause remains unproven. |
| Initial other-app playback baseline | A temporary, separately signed iOS QA app played 15 seconds of nonmixable audio. Without CallKit and with no inbound audio, the phone later disappeared from the browser participant list and recovered on foregrounding. Repeating while the browser actively sent synthetic audio retained two participants during playback and for over a minute afterward. No app crash was seen. This is a controlled competing-audio test, not an X/Instagram test. |
| Audio session | Before join the app requested `.playAndRecord` / `.videoChat` with options 5 (`mixWithOthers` plus Bluetooth HFP). The SDK changed it after join to `.playAndRecord` / `.voiceChat` with options 36 (no mixing). A guarded restoration produced options 37, yet the competing-audio/background disconnect still occurred. |
| SDK CallKit experiment | Enabling the SDK's `isCallKitSupported` flag showed a system call UI stuck at “Connection…” and the browser never saw the phone join. The experiment was removed. |
| App-owned outgoing CallKit call | With `UIBackgroundModes` containing `voip` and `audio`, the app's `CXStartCallAction` activated an audio session and the SDK joined only after `provider(_:didActivate:)`. The browser saw the phone with microphone and camera Off. The system call showed connected after SDK active phase. The SDK CallKit flag remained disabled. |
| Silent background with CallKit | With both local streams Off and no inbound publisher, the phone remained listed for over seven minutes while the app was backgrounded. The user then physically locked iVitalii for about one minute; the browser still listed the phone. This reverses the initial baseline failure in the tested meeting, but does not complete a 30-minute soak. |
| Competing playback with CallKit | The temporary QA app played a 15-second nonmixable tone during a muted, silent-room conference. The browser retained two participants during playback and for over a minute afterward. Audible conference output was not assessed during the competing playback. |
| Leave with CallKit | A DEBUG timed Leave after 100 seconds in the background initiated `CXEndCallAction`; the browser dropped from two participants to one and the app returned to “Left the meeting.” |
| Incoming cellular call | The first implementation omitted `CXSetHeldCallAction` and the phone left the meeting during an answered cellular call. After hold handling was added, a second answered call kept two remote participants, but the app did not automatically unhold. With call observation and resume recovery added, a third answered call produced hold, unhold and audio-reactivation callbacks; the browser stayed at two participants with the phone's mic/camera Off. Afterward a second browser participant published a synthetic microphone tone and the user confirmed hearing it on iVitalii. |
| Packaging | The SDK package omits `Spench.framework` from its product although the binary loads it. The build script embeds the matching framework; simulator and device launch succeeded. |
| Thirty-minute locked call | With local microphone/camera Off and no inbound publisher, the user locked iVitalii for roughly 30 minutes. A browser observer sampled the participant list every 30 seconds and continued to see the phone throughout. While the phone was still locked, the browser began publishing a synthetic microphone tone; the user confirmed hearing it through the locked phone. |
| Incoming video | A browser published a synthetic video feed. A device screenshot showed its green moving frame rendered in the native conference view while the phone's microphone and camera remained Off. |
| Explicit media publishing | The physical-device UI test enabled microphone and camera, flipped the camera, then turned both streams Off. The browser independently showed the phone's microphone and camera On, then Off. The test passed after the user granted the provider and iOS camera prompts. This confirms publishing state; intelligible speech and camera image quality were not measured. |
| X and Instagram playback | During a meeting with browser-published tone and video, the user played video with sound in both X and Instagram and reported that conference audio was not paused. The browser retained the phone as a participant with both local streams Off. Exact audio mixing levels were not measured. |
| Audio routes | The user switched among speaker, AirPods and iPhone earpiece and reported that each route worked while the meeting stayed open. The user also spoke with microphone enabled through AirPods and then iPhone; the browser showed Mic On/active-speaker indication, then Mic Off. The browser did not identify which physical input supplied each phrase. |
| Active-call link replacement | A second custom-scheme invitation arrived while the first room was active. The app requested confirmation to leave; the first room lost the phone, the second invitation became ready, and the second browser room listed the phone with Mic Off/Camera Off after Join. An initial run exposed a stale terminal callback overwriting the ready status. The guarded fix passed a repeat manual run and an opt-in physical-device UI regression test (`/tmp/rocknroll-link-ui-external-20260923.xcresult`, 1 passed). |
| Web handoff page | A local Playwright browser check verified a prefilling `?url=` parameter and the handoff button, and confirmed that an invitation with duplicate `psw` parameters is rejected. A physical Safari tap on that page was not included. |

The original unsigned simulator/device builds and simulator join-screen launch passed before this device run. The current signed physical build and both opt-in media/link UI tests passed after the view-container change; the simulator UI smoke test passed with the live media test skipped. `ConferenceCore` previously passed all four unit tests with the full Xcode developer directory selected. The vendor framework copy needed writable permissions before code signing in the simulator build. A plain UIKit parent for the SwiftUI join screen and SDK conference view removed the `UIHostingController` subview warning in the latest media test. XCTest still reported active-audio main-thread warnings in both tests, and a state-publication-during-view-updates warning in the latest warm-link test; these deserve follow-up even though the tests passed.

**Not yet accepted:** intelligible two-way speech and camera image quality, microphone-on competing playback, FaceTime/Siri/other-VoIP interruption, wired/USB routes, network handoff/reconnection, cross-organizer guest policy, and a physical Safari tap through the custom-scheme handoff page. Owned-domain Universal Links are outside the chosen handoff scope. The locked-call test verified a synthetic tone after silence rather than a long two-way conversation.

The initial `UIBackgroundModes=audio` plus `.mixWithOthers` setup failed silent-room background membership. The later genuine outgoing CallKit call passed the 30-minute silent/locked run, post-silence inbound tone, controlled competing-player, real-app playback, and route checks above. The browser observers left both test rooms, the UI tests left and stopped the phone app, and the temporary competing-audio app was uninstalled.
